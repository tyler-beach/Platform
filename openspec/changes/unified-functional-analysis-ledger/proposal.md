# Proposal: Reconcile Functional Analysis runs with the audit ledger

## Why

The repository currently has two runnable analysis paths with different audit behavior. The PoC analysis workflow writes findings, evidence, confidence components, and run events to CSV files on the `poc-database` branch. The Tree-sitter Functional Analysis Demo produces a versioned GitHub Actions artifact, but does not create a CSV ledger record or a confidence assessment. Pages can show its workflow status, but the two paths cannot yet be explored as one audit trail.

This is a design gap, not a claim that the deterministic Functional Analysis mock has measured confidence. Its selected fixture oracle is a test expectation, not a confidence signal.

## What changes under the proposed direction

- Define a stable, versioned audit record for a validated Functional Analysis run, linked to its repository, run ID and attempt, pinned input hashes, evidence IDs, outcome, validation checks, and original Actions artifact.
- Persist this record idempotently in the existing CSV ledger so repeated delivery of the same workflow run cannot create duplicate logical records.
- Keep workflow execution state, analysis/validation state, and domain outcome as separate fields. A canceled or failed run may have no domain outcome.
- Add reconciliation that detects completed or canceled workflow attempts that are missing from the CSV ledger; a concurrency queue is not treated as durable storage.
- Store the new workflow-run record in an additive CSV table; do not change existing table headers or reinterpret existing finding/run rows.
- Keep evidence-strength scoring separate from fixture-oracle agreement. Reuse the existing scoring algorithm only after its required evidence/linkage inputs are present and validation succeeds; otherwise record confidence as unavailable with a reason.
- Extend the Pages projection to show the joined run, outcome, evidence summary, confidence availability, and trusted link to the original Actions run/artifact page, subject to the existing private Pages gate.

## Scope and non-goals

This change would unify the audit record for the synthetic Functional Analysis workflow and the existing PoC ledger. It does not make the Tree-sitter mock an LLM, infer calibrated probabilities, publish raw workflow bundles or source excerpts to Pages, add production code ingestion, or enable AI-only merge blocking.

## Acceptance criteria

- A successful validated Functional Analysis run produces one versioned ledger record with exact source hashes and stable evidence references.
- Execution status, analysis/validation status, domain outcome, and persistence/reconciliation status are represented independently. A technical failure is not a domain outcome.
- Existing CSV headers remain unchanged; the new record uses a versioned additive table and can be read alongside existing ledger data.
- Replaying the same repository/run ID/attempt does not append a duplicate logical record; a different attempt remains separately auditable.
- Failed, cancelled, or invalid runs remain distinguishable from domain outcomes and are not recorded as successful assessments.
- Fixture-oracle match is never reported as confidence or quality evidence.
- Confidence is either computed by the existing versioned evidence-strength algorithm from its required validated inputs, or explicitly unavailable with a reason.
- The Pages projection contains only allowlisted summary metadata and validated links. It does not contain raw source, prompts, model payloads, secrets, or downloaded bundles.
- Ledger writes serialize with the existing CSV writer and have bounded conflict/retry behavior. Queue overflow or exhausted retries are detectable and reconciled; the workflow never claims exactly-once execution.
- A scheduled reconciliation finds eligible recent default-branch workflow attempts absent from the ledger, persists execution-only records when no validated analysis result exists, and reports attempts that can no longer be recovered from retained artifacts.
- Only completed successful Functional Analysis runs from the repository default branch can contribute a validated analysis result to the shared ledger. Pull-request and non-default-branch runs remain in Actions history/artifact storage only.
- Public Pages, user-owned repositories, pull-request runs, and unverified Pages visibility cannot publish detailed run records.

## Risks and rollback

The Functional Analysis workflow currently has `contents: read`. Ledger persistence needs write authority or a separate trusted writer, which expands the security boundary. A downloaded artifact is untrusted input even when generated by a workflow; the writer must validate its run identity, attempt, manifest hashes, schema, size, and evidence references before persistence. GitHub Actions concurrency is not a durable queue: its default permits one pending run and replaces that pending run when another queues. Even its bounded multi-run queue has a finite limit, so reconciliation remains necessary. CSV-on-branch remains a single-runner PoC store and must serialize only the write operation across both writers. If these controls are not acceptable, keep the workflows separate and clearly label the Functional Analysis artifact as run-scoped rather than ledger-backed.

Rollback disables the Functional Analysis ledger writer and Pages projection; already written immutable run records remain historical data and require a separate retention decision.

## PoC implementation direction

The user directed implementation and integration of the shared audit trail. This PoC uses an additive CSV table, a separate artifact-consuming writer, default-branch-only validated ingestion, a 13-day reconciliation horizon against the 14-day final artifact retention, and the existing private Pages gate. The workflow exposes confidence as unavailable because the fixture oracle does not satisfy the evidence-strength algorithm's input contract. These choices authorize the synthetic PoC implementation; they do not approve production ingestion, live credentials, calibrated confidence claims, or AI-only merge blocking.

The repository's 50-case corpus is synthetic and unadjudicated. It must not be used to claim calibrated confidence or production quality thresholds.
